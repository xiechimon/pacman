# ADR 0011 · 总管过程按事件边界实时封段，流式与落库同源

> 状态：**已裁决**（2026-10-06）。落地票 #955（挂 #908 地图，`chief.css` 不动）。
> 来源：用户观察——「他所有的对话都在一个对话框中，并且一直不停地生长，直至完成这个任务。他没有把这个状态分开吗？」——加上一次对 Multica 的源码级调研（`docs/research/r15-multica-run-rendering.md`，HEAD `b4ca5b4a`）。

## Problem Statement

总管跑一个回合时，整轮叙述被拼成一个不断变长的文本块：中间看不到它调了什么工具，也无法分辨「哪句是上一轮说完的、哪句是这一轮刚想的」，直到回合收尾才**一次性**分开。

这不是渲染没分开，而是**拼的时候就拼成一串了**。

## 侦察事实

| # | 事实 | 出处 |
|---|---|---|
| F1 | 一轮 = 一个 step = 一个 `activeRun`；在飞期间整轮 `text_delta` 进**一个字符串缓冲**（`append` 即字符串相加，不插分隔），只画一条 typing 尾行 | `apps/web/src/api/live-text.ts`、`apps/web/src/api/mappers.ts` `mapChief` |
| F2 | assistant 文本行**只在步收尾落库**（`message_end` 只写本地 journal，终稿经 `upload-urls` 一次性上传）；轮中唯一实时落库的是工具行 | `apps/daemon/src/runner.ts`、`apps/server/src/services/machines.ts` `reportTool` |
| F3 | 实物：`docs/verify/857/tail-samples.jsonl` 里三轮叙述拼成一行、共享**一个**身份 chip | `docs/verify/857/` |
| F4 | Multica 的切分在**写入端**：连续同类型增量攒缓冲，遇类型变化 / `tool_use` 到达 / 窗口 tick 封口；**先落库再广播**；实时行与终稿行**共用一个稳定行键** | `docs/research/r15-multica-run-rendering.md` §2/§6 |

## Decision

| ID | 裁决 | 理由 |
|---|---|---|
| **D1** | 切分在**写入端**（daemon runner）：每步维护「当前段」缓冲，触发封口 = 类型变化（text ↔ thinking）/ `tool_use` 到达 / `message_end` / 步收尾 | 客户端切分需要猜边界；写入端有真值 |
| **D2** | 封段行**实时上报**（machine tool 第五形），server **先落库再广播** | 中途进场者靠 REST 重取天然拿到已完成的行；补发面只剩「当前未封段」 |
| **D3** | 落库的 assistant 行形状 = **单类型块数组**（`[{type:'text'}]` / `[{type:'thinking'}]`）；`tool_use` 不再进 assistant 行 | 段即行；存量原始块数组行照旧可读 |
| **D4** | 段 id 沿用 `msg-<stepId>-<seq>`，`seq` 从「每条 `message_end`」改为「每次封段」；`createdAt` 强制单调（`max(now, last+1)`） | 终稿上传与实时上报同 id 幂等；同毫秒并列会让排序不稳 |
| **D5** | **显示思考行**，接受它进界面与公开证据图 | 用户裁决。风险已具名：思考常含复述的提示词与用户数据，而本仓验证截图提交进公开仓 |
| **D6** | 工具行**流式期平铺、`activeRun` 收口后折进后续行的披露** | 保留 r5 canon 的落库形；与 Multica「流式展开、settled 折叠」同构 |
| **D7** | 服务端清缓冲**只由 assistant 文本行触发**，工具行不再清 | 迟到工具行会抹掉正在流的下一段；改后两侧统一为「缓冲 = 当前未封段的文本」 |
| **D8** | **客户端不做任何切分** | D1 + web 既有 #857 handoff 已经让每段自动落成一条行，切分逻辑无存在必要 |
| **D9** | 详情页（worker 步）**同改** | 共享同一套 daemon 封段；两面同形，不给共享层加分支 |
| **D10** | **不引进** Multica 的 preface / middle / final 过程分层 | 属「一轮一行、行内 step 列表」那一波；本票只解决「跑的时候挤成一坨」 |

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| **客户端按工具行切缓冲** | 客户端只看得见工具行、看不见段的文本归属；且中途进场的补发是一条粘好的字符串，没有偏移量可切 |
| **只在 `message_end` 上报（不改封口时机）** | 与「工具行流式可见」**数学上不相容**：工具行在工具**开始**时上报，必然先于它前导文本落库，UI 上工具会显示在文本上方、轮末再跳进折叠 |
| **封口只封文本（thinking 丢弃）** | 会让「显示思考」变成必须新开一条通道的孤岛；按类型封口反而让思考成为封口的副产品 |
| **维持现状** | 用户报的就是现状 |

## Premortem（假设已失败，最可能死因 + 护栏）

| 死因 | 护栏 |
|---|---|
| **段序翻转**（同毫秒并列、迟到工具行） | D4 单调 `createdAt` + D7 清律；真 e2e 断言「文本段在前、其工具行在后」 |
| **终稿上传与实时行双份** | 同 id 幂等 upsert（既有 `onConflictDoUpdate`）+ 断言「该段文本恰出现一次」 |
| **落库形状变更打坏存量读侧** | `textOfContent` 两种形状都吃（字符串 / 块数组）；存量行不迁移 |
| **思考原文进公开证据图** | 证据图一律用折叠态截图；需要展开态时手写裁剪，且 PR 前自查截图内容 |
| **详情页与抽屉分叉** | D9 同改；两面共用 mapper 产出的行序列 |
