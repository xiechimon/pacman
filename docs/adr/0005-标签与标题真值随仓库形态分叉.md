# ADR 0005 · 标签与标题的真值随仓库形态分叉

> 状态：**已裁决**（2026-09-30）。
> 来源：#446 的分诊与 grill（2026-09-29 ~ 09-30），原始反馈 =「标签应该映射到具体的 issue 上」。
> 关系：本 ADR **收窄 ADR 0002 D2/D3/D4 的适用域到 local 形态项目**，并记录 github 形态的改判；ADR 0002 的其余裁决（D1/D5/D6/D7）全文继续有效。
> 编号说明：0004 已被在途车道 #447（总管面板形态）占用，本文件取 0005；若 #447 未合，合前按仓里「序号以合并时点 main 尾部为准」的纪律重编。

## Problem Statement

标签自 ADR 0002 D4 起 = 固定 6 词表（bug / feature / improvement / refactor / docs / chore）、随项目播种、每任务至多 1 个、派发时由执行 agent 回填。标题自 ADR 0002 D2/D3 起 = 正文首行占位截断，执行 agent 接单后回填正式标题。

这两条裁决的共同前提是：**pacman 是元信息的唯一真值源**——没有别处已经写过这份元信息。但这个前提对 GitHub 形态的项目不成立：仓库侧已经有一份**人写的** issue（标题 + label 都在），同一个任务在两处各握一份真值。用户要的不是「换个词表」，而是问「真值放哪一侧」。

## 侦察事实（2026-09-30 实测，逐条出处）

| # | 事实 | 出处 |
|---|---|---|
| F1 | server 的 GitHub 面只有**连接与仓库列表**：`lib/github.ts` 只调 `/user` 与 `/user/repos`；issue 读面、label 面、建 issue 面全不存在 | `apps/server/src/lib/github.ts`、`apps/server/src/services/github-connection.ts` |
| F2 | OAuth 请求 scope = `read:user repo`（`GITHUB_CONNECTION_OAUTH` 单源），`repo` 已含 issues/labels 读写 → 本裁决**不需要新 scope** | `apps/server/src/services/oauth.ts`、`apps/server/src/lib/github.ts` 的 token 交换 |
| F3 | 执行面 github 形态 = executor 拿 `x-access-token` 直连远端推 conv 分支；**不建 PR、不建 issue**，`build.prUrl` / `prNumber` 列存在但恒 null | `apps/daemon/src/runner.ts`、`apps/server/src/db/schema.ts` |
| F4 | 「每任务至多 1 个标签」**只活在文本与提示词里**：`todo.tagIds` 本就是数组，`todo_tag` 是 `(todoId, tagId)` 主键的纯 join 表；约束的实际落点是 ADR 0002 正文、`set_task_meta` 的单 `tag` 参数、daemon 注入的提示词三处 | `apps/server/src/db/schema.ts`、`packages/shared/src/protocol/chief-tools.ts`、`apps/daemon/src/runner.ts` |

| F6 | `todo` 已有溯源家族（`sourceTodo` / `createdBy` / `ownerId` / `sourceBuildId`），来源绑定可归入同族 | `apps/server/src/db/schema.ts`、`packages/shared/src/records/todo.ts` |
| F7 | 用户实例今天**零使用面**：`github_connection` 零行（从未连过 GitHub），唯一项目还是 legacy `hosted` 形态 | `~/.pacman/server/server.db` 实测 |

## Decision

| ID | 裁决 |
|---|---|
| **D1** | **分叉律**：`githubRepo` 形态的项目，**标签与标题的真值都在 issue 上**；`local` 形态的项目，两者都留在 pacman 内。ADR 0002 D2/D3/D4 的适用域据此收窄为 local。 |
| **D2** | **词表来源分叉**：github 项目的标签词表 = 仓库实际的 label 集（动态）；local 项目 = 固定 6 词表（ADR 0002 D4 原样）。词表来源是「标签」的属性，**不是新实体**。 |
| **D3** | **词表落地**：仓库 label 按 `(projectId, name)` upsert 进 `tag` 表，颜色取 GitHub 的 color。仓库侧后来删掉的 label **保留行**——删行会经 `todo_tag` 级联摘掉任务已挂的标签，标签的历史不该被外部仓库改写。 |
| **D4** | **标签数量分叉**：github 项目放开（issue 挂几个贴几个）；local 项目仍至多 1 个。「至多 1 个」在 github 侧作废的理由：那条限制的初衷是消灭**人工**挑标签的微决策（ADR 0002 premortem），而 issue 的 label 是人已经贴好的事实，不是要现挑的选项。 |
| **D5** | **标题来路分叉**：从 issue 建的任务直接用 issue 标题，不走占位→回填两段式；local 项目照旧两段式。 |
| **D6** | **任务有「来源」**：任务可绑定一个外部出处（当前只有 GitHub issue 一种），绑定归入 `todo` 现有溯源家族。 |
| **D7** | **本裁决只定真值与形态，不含写向**：自派任务也在 GitHub 建 issue、把回填标题写回 issue = 独立后票；自动同步与相位回写同样不在本裁决内。 |

## Premortem（假设已失败，三种最可能死因 + 护栏）

| 死因 | 护栏 |
|---|---|
| **两个真值源漂移**：仓库侧改了 label 名 / 删了 label / 改了 issue 标题，pacman 不刷就与仓库不一致 | D3 的保留行保证「已挂的标签不会凭空消失」；导入面每次现拉，不缓存成第二个真值。票面把「仓库改了，pacman 至少不变得更错」写成验收条件，而不是承诺一致。 |
| **词表失控**：真实仓库的 label 动辄 20+ 个，混着 `needs-triage` / `area:*` 这类流程词，agent 与用户都失去分类价值 | **不在 pacman 侧做名字启发式过滤**——过滤规则会随仓库改名而碎，且会静默吞掉用户真实用到的词。词表就照仓库的真相；版面问题交给卡片渲染的上限，不交给词表。 |
| **分叉变成两套规则**：同一个看板上 github 任务多标签、local 任务单标签，实现里长出两套分支 | 两侧共用一条不变式——**贴的标签必须在本项目标签集内**（github 项目 = 仓库 label 镜像，local = 6 词播种）。`set_task_meta` 的校验从「白名单 6 词」改成这条不变式，数量上限成为调用面的参数而不是词表的性质。 |

## Consequences

- **正向**：真值各归其位——github 项目的元信息跟着仓库走，人在 GitHub 上写的东西不再需要在 pacman 里重打一遍；数据面几乎不用动（F4），放开多标签是免费的；配色白拿（F5）。
- **负向**：**同一个概念长出两套语义**（词表来源、标签数量、标题来路三处都按仓库形态分叉）。这是本裁决最主要的代价：`CONTEXT.md` 相应词条必须写明限定，否则下一个读者会默认两边一样。分叉的正当性来自「local 项目根本没有外部真值可依」——不是偏好，是约束。
- **零使用面**：F7——用户实例从未连过 GitHub，本裁决是为将来的 github 形态项目定形。它今天不改变任何现存行为，local 项目侧一字未动。
- **与 ADR 0002 的关系**：收窄，不是推翻。local 项目的标签与标题行为与 ADR 0002 裁决当天完全一致。
- **重开触发**：写向后票落地后重新审视 D7 的边界（哪一侧是 source of truth 会从「各管一段」变成「谁覆盖谁」）；出现第二种来源（PR / CI 失败 / 外部工单）时重审 D6 的形状；local 项目开始有人抱怨「为什么我的仓库不能有真标签」时重审 D2 的分叉（那是把可编辑词表请回来的信号）。
