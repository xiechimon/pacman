# ADR 0014 · chief 派发判定（先规划/直接修）：判定权归 chief——判、说、可推翻

> 状态：**已裁决**（2026-10-08，用户裁决推翻第一轮核心结论）。落地票 #903 返工轮（PR #1016）。
> 前身：本票第一轮交付的 ADR《0013-chief派发方式-选择权归人-服务端强制》——只存在于 PR 分支、从未合入 main，随返工删除并由本文件整体承接（旧裁决逐条处置见「旧裁决翻转记录」，不悄悄删）。main 上的 0013 编号属《总管面板形态-悬浮窗》（#1047），与本票无关。
> 依据 = `docs/research/892-gate-usage-measurement.md`（量闸实测，事实编号沿用）。

## Problem Statement

真问题不变（#892 实测）：主派发路径上 confirm 闸被编排者单方撤销——`run_builds` 工具默认 `withPlan:false`，系统提示词工作约定又明令「withPlan:false 直接执行」，两处写死互相联动，chief 派发 8/8 全部直执行，用户既无入口表达意向，也无从得知每次派发为何直执行。

返工轮修正的是**问题定性**。第一轮 ADR 0013 把病灶定性为「chief 有权」，于是没收判定权：全局设置槽 `chief.dispatchWithPlan` + 服务端 clamp（工具面除名 withPlan 参数）。用户 2026-10-08 裁决指出：**以前出问题不是因为「chief 有权」，而是权力被写死在工具默认值和提示词两处、且不对用户说明——要治的是不透明，不是有权**。这句话是本次推翻的唯一正当理由。

没收式修法有两处站不住：① 全局开关要求用户在任务上下文之外，预判所有未来任务是否需要方案——而真正能做这个判断的是看着任务本身的 chief；② 设置槽并没有消灭不透明——用户设了「先规划」之后，chief 对每张具体的票为什么走这条模式，依然一个字不用解释。透明的形态是**判、说、可推翻**：判定权归 chief（判），每次派发写明理由（说），用户就地一句话能改（推翻）。

## Decision

| ID | 裁决 | 理由 |
|---|---|---|
| **D1** | **判定权归 chief，设置槽删除。** `withPlan` 回到 `run_builds` 工具面，成为 chief 的逐次派发判定参数；`chief.dispatchWithPlan` 设置槽整体退场——DB 列、PATCH 槽、封套投影、settings UI 行、fixture 场景、i18n 键一并删干净，不留哑控件。服务端保留的唯一机械保证 = 缺省默认值（D2），零判定规则 | 见 Problem Statement：治不透明不治有权。迁移从未合入 main（第一轮 0027 撞号，返工轮重编为 0029 后随槽删除），无存量库负担 |
| **D2** | **判不准 → 默认先规划。** `run_builds` 的 `withPlan` 缺省 = true（`bool(params,'withPlan',true)`）；提示词判定节同文写明「判不准 → 先规划」「withPlan 缺省即先规划」 | fail-safe 方向必须是「多问一次」，不是静默跳过闸。**原 ADR 0013 D2 的论证原样成立**：① 两道硬闸是产品主张（spec 18），缺省面不应单方撤销 confirm 闸——#892 的 8/8 病灶正是「默认即撤闸」（F1/F3）；② 用户数据 94% 选带方案（F2）。变的只是载体：列 DEFAULT true → 工具参数缺省 true，语义同构、面更小 |
| **D3** | **「直接修」只跳过 confirm 闸，review 闸永远在。** `withPlan=false` 只决定首步 kind（build 而非 plan）；review 闸在合并路径上，与本参数无涉 | 两道硬闸是产品主张（`docs/spec/18-定位与差异化.md`）；跳过 review = 发布前无人把关。multica 能拆闸是因为它本来没闸（F4）；pacman 拆了就是拆自己的卖点。结构上 review 闸也从不读 withPlan——这条是「不可能被本机制跳过」，不是「约定不跳过」 |
| **D4** | **判 + 说 + 可推翻。** 判：chief 逐次定 `withPlan`。说：判定理由写进 `run_builds` 的 `dispatchReason` 参数（随工具调用落 transcript/chief_message，可回查审计，F1 通道），且提示词责令回执写明「我判为直接修 / 先规划，因为 X」；响应回显 `dispatchReason` 供 LLM 自检。可推翻：用户就地一句话推翻，**只影响这一次**（已开跑的 cancel_builds 后按相反模式重派），不外推为常设偏好 | 判定不可审计 = 换了个黑箱，等于没改。说（transcript 实录 + 回执 prose）与推翻（就地一句话）是「chief 判定」与「chief 专断」的全部区别；「只影响这一次」防止单次推翻悄悄变成新默认——那会复活设置槽语义却不走设置槽的审计面 |
| **D5** | **判据写章程 prose，不写成代码里的规则表。** 系统提示词派发判定节给三条**可判信号**（非硬规则）：有可复现步骤或失败测试的缺陷 → 直接修；引入新能力、或改动跨包 → 先问；判不准 → 先规划。出厂只留一条**判断纪律**（不是工作流），照抄 multica 内置 Chief of Staff（Mika）指令原句（F5）：「当信息会实质改变结果、执行方式、权限或安全时才问；否则自己决定，并说出你决定了什么。」判定节为静态文本，不按任何设置合成 | 规则表迟早变成第二个 `withPlan:false`——任何写进代码的判定逻辑都会像原工具默认值一样硬化成不可审计的行为（F3 是前车之鉴）。「缺陷还是新能力」本身是需要任务上下文的语义判断，LLM 正是判断者；服务端只留 fail-safe 缺省（D2），零规则。「提示词描述与实际行为一致」（原 D4 的要求）承接：静态判定节描述的就是真实工具面——参数在词表里、缺省语义与参数 description 一致 |
| **D6** | **产品只提供机制，不提供政策。** 把某个技能（如 `grill-with-docs`）的形态写进 chief 默认行为 = 把用户的个人工作流焊进产品。**触发权归用户**：用户点名才走那条流程 | multica 镜像（F4）：不内置任何工作流正是它的适配面——行为由自由文本决定，无代码分支。pacman 的机制 counterpart 已齐：章程（用户可写）+ 技能全量可见（F6）+ 建议性路由节（F7）。机制之外出厂任何政策都是越权 |

## 回读校验

本 ADR 的裁决载体是代码行为面（工具词表参数 + 提示词静态判定节 + 设置槽死态），不是服务端快照式配置记录。回读面 = `docs/verify/903/`（返工轮）live 证据链：假机器 relay `run_builds` 三形态（缺省 / 显式 false + 理由 / 显式 true + 理由）的响应回显 + 首步 kind 落库行 + claim 载荷 systemPrompt 判定节实物 + 设置槽死态（PATCH 400、封套无 `dispatchWithPlan` 键、Agent tab 无「派发方式」行）。
