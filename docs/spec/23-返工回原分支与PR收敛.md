# 23-返工回原分支与PR收敛（issue #931）

> 策略正本：返工（审核关口打回 + 失败重启带反馈）回到原分支/原 PR 继续的
> 裁定、机制与存量收敛规则。票面正本 = issue #931；实现偏离须回改本文。

## 1. 事实（实测，非推断）

- buildId ≡ conversationId ≡ 分支名（`brand.ts conversationBranch`，
  `pacman/conv-<uuid>`，schema.ts build 表头注）——**新 build 必然新分支**，
  这是「返工另起 PR」的结构性根因，不是某处漏写。
- 两条返工路此前不同源：`revision`（#701）本就同 build 入队重规划步（分支
  天然保留）；`restart`（#320/#720）`newUuidv7()` 另起 build → 分支被扔。
  票面现场：todo `q5ULhY_3exxQPatM4ZkFm` 同一改动同时开着 PR #888 与 #928。
- PR 字段（build.prUrl/prNumber）只由 github 形态项目的 daemon 步收尾探测
  回填（`runner.ts` prProbe → `finishStep`）；hosted/local 项目恒空。

## 2. 裁定（用户 2026-10-05）

- **R1：有 PR 的任务，任何返工回原分支。** 审核关口打回、失败重启带反馈
  两条路都算——返工落「那一刻最新的产过 PR 的 build」上：同
  conversationId = 同分支 = 原 PR 就地收新提交。**一个 todo 任一时刻最多
  一张 open PR。**
- **R2：只复用分支，会话全新。** 复用轮首步强制新引擎会话（step.freshSession
  → claim `session.action='new'`），daemon 以「任务全文 + 返工指令」组合串
  （#720 形）开全新会话；工作区回退到分支已提交态（上一失败轮的未提交残渣
  不带入）。分支连续性与会话真空是两个维度，都按裁定执行，不悄悄二选一。
- **R3：原 PR 已合并/已关闭才允许新分支，且判定可见。** restart 时刻服务端
  探一次 PR 状态（github_connection token → 匿名梯）；closed → 新 build +
  新 conv 落 system note（`buildReworkNewBranchNote`）点名旧 PR 与新分支名
  ——用户能看出「为什么这次是新 PR」。**探测失败 = fail-open 复用**：误开
  新分支会把 R1 的 bug 原样带回，误复用已合并分支只是提交落旧分支（可见、
  可收拾），代价不对称。
- **R4：无 PR build 的常规重启不变。** 无 PR 字段 → 现行新 build/新 conv 行为
  逐字节保持（`startBuilds` 家族语义：全新执行）。

## 3. 机制（server 侧判定 + daemon 侧消费）

- **判定位** = `builds.ts applyBuildStepAction` restart 分支：`latestPrBuild`
  （todo 最新的 prUrl/prNumber 非空 build，createdAt 降序）→ `probeReworkTargetPr`
  → 复用路（不建新 build；反馈行 + `buildReworkReuseNote` 落旧 conv，后者承接
  被清空的 build.errorMessage 失败原文；首步 freshSession 置位；build 行
  errorMessage 清空 / prevPhase='failed' / pin 回落 todo.machineId）或新建路
  （现行行为 + prClosed 在位时的判定 note）。
- **claim 面**（`machines.ts tryClaim`）：freshSession 步 `session={action:'new',
  sessionId:null}`，且不进 #863 会话亲和闸（新会话无会话文件依赖，不为他机
  留步）。复用轮后续步（confirm 后执行步、打回重规划步）照常 continue 该轮
  新开的会话——review-reject 路与 restart 路自此同源。
- **daemon 面**（`runner.ts`）：fresh session + reused worktree →
  `restoreCheckpoint` 回分支头（canon 行「返工新会话：工作区回退到分支头」）；
  worktree 已被孤儿回收（TTL 7d）的形态 `prepare` 本就从 origin/<branch> 重建
  （02 §5.5 既有护栏）——「旧 build 已收尾、工作区已回收」不是另起分支的理由。
- **plan 版本**：复用 build 上 `receivePlanUpload` version=max+1 自然 v2/v3，
  diff 面零改动。

## 4. 存量收敛规则（一 todo 多 open PR 的既有数据）

- 返工恒落**最新**的产过 PR build（`latestPrBuild`）；更旧的 PR build 属被
  取代分支，不再入轮、不自动关闭。pacman **不代用户关 GitHub PR**（对外写
  操作，正站无此先例）——更旧的 open PR 由用户手关（#931 事故现场 #888 即
  如此处理）。
- 机制保证新数据不再翻倍：复用路收敛到单 build 后，后续返工仍命中同一
  PR build，分支数不随返工次数递增。
- `latestBuildId` 在 legacy 形态（最新 failed build 无 PR、PR build 更旧）下会
  指回 PR build——「当前轮在哪个 conv 跑」的真值优先于单调时序；修后新数据
  不出现该形态（复用使 PR build 恒为最新）。

## 5. 边界（本裁定不覆盖的入口——重跑 ≠ 返工）

- `startBuilds` 三入口（REST 人工启动、chief `run_builds`、定时复跑）仍造新
  build 新分支：重跑语义 = 全新执行，不是返工。若用户在此入口也要回原分支，
  另开票裁（涉及「全新执行 vs 继续」的语义分叉，不并进本票）。
- hosted/local 项目无 PR 探测面，PR 字段恒空 → R1 条件永不触发，返工行为
  与现状一致（新 conv）。
- review 步恒新会话（#511）与本机制共用「强制 new session」判据族但各归各面
  （review 的只读护栏不受复用路影响）。
